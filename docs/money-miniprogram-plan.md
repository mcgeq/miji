## 1. 现状分析：现有 Money 功能全景

### 1.1 应用定位

米记（Miji）是**本地优先（local-first）**的跨平台个人记账 + GTD + 健康管理 App（Flutter + Riverpod + Drift/SQLite，schemaVersion=20，约 55 张表）。**无自有后端**，可选 WebDAV（坚果云等）增量同步 + 加密快照备份。记账（Money/bookkeeping）是体量最大、最核心的模块。

### 1.2 Money 功能模块全景（现有 App）

记账 Tab（`/app/bookkeeping`）内 8 个分区，另有首页仪表盘与全局快捷入口：

| 分区 | 能力 | 关键点 |
|---|---|---|
| 账户 accounts | 17 种账户类型（现金/银行/信用卡/花呗/白条/美团月付/储蓄/投资/贷款/支付宝/微信/云闪付/预付卡等），期初余额 + 当前余额，信用卡额度/已出账欠款/冻结额度/账单日/还款日，软删除可恢复 | 信用类账户余额语义反转（显示可用额度） |
| 流水 transactions | 支出/收入/转账三种类型；退款（refundAmount）；状态 completed/pending/voided；标签；商家/地点/备注；多条件筛选分页（账户/分类/支付方式/日期/关键词）；最近商户与支付方式自动补全建议 | 转账落地为成对两条流水；还款=转账+语义标记，无独立还款类型 |
| 统计 statistics | 趋势（日/月分桶）、分类/子分类占比、支付方式、账户分布、商户排行、家庭成员分摊、环比/同比、时段/星期分布、退款率、来源分析（分期/自动记账/其他）、信用利用率、预算执行、净资产趋势、支出异常检测（top20 涨幅>20%）、90 天现金流预测、周期报表（JSON 快照） | 全部实时聚合，非缓存；周从周一开始；区间半开 [start, end) |
| 分类 categories | 两级扁平结构（一级 + 二级平铺表），支出/收入向，系统内置 + 自定义，图标/颜色，软删除 | 排序靠使用频率，非 sortOrder |
| 预算 budgets | 支出限额/收入目标两用；作用域 4 种（全局/分类/账户/分类+账户）；周期 5 种（日/周/月/账单周期/年，可 repeatInterval）；子分配（按分类/成员，支持权重/固定/比例、超支控制、预警阈值默认 80%、强制、优先级）；自动滚存；历史快照 + 版本号 | 已用额实时 SQL 求和，快照用于趋势与同步 |
| 分期 installments | 计划（本金+利息+期数）+ 每期明细（期号/本金/利息拆分/到期日/状态），到期入账自动生成流水（冻结→已出账），批量执行，修复状态 | 生成的流水禁改删 |
| 自动记账 autoPosting | 定时模板（日/周/月，dayOfMonth/weekday/timeOfDay）+ 执行记录（occurrenceKey 幂等），状态机含 duplicateIgnored/blocked/retryableFailed/userDeleted；待执行金额预计入预算 | 依赖本地调度 |
| 提醒 reminders | 账单提醒（手建/信用卡还款自动生成，金额可静态或实时取欠款，日/周/月/年重复）；提醒中心（预算超支/信用卡账单/分期/周期支出/账单五源聚合，优先级排序，稍后提醒/完成/忽略，itemKey 幂等） | 提醒中心为无存储派生视图，仅处理状态落库 |

其他：账本（个人/家庭）与账户/交易多对多关联；成员 + 分账（均摊/固定/比例/权重/自定义规则，一次交易一个活跃分账）；首页仪表盘（今日/本月收支、预算节奏、分类结构、最近 5 笔、紧急提醒、7 天柱状图）；全局 FAB 8 个快捷动作（支出/收入/转账/任务/账户/分期/预算/计划）。

### 1.3 领域模型核心约定（迁移蓝本）

- **金额一律 int 分单位**（amountMinor/balanceMinor），无浮点；格式化为元由 `money_amount_formatter.dart` 负责。
- **单币种记账，无汇率换算层**（10 种币种并列，统计仅提示 hasMixedCurrencies）。
- 软删除（isDeleted/deletedAt）+ 乐观锁版本号（version）贯穿所有同步表。
- 枚举持久化用 kebab/snake_case 字符串，带 fromStorageValue 兼容历史 PascalCase。
- 交易↔账本为**多对多链接表**（交易实体无 ledgerId）；个人账本不可解绑、有活跃分账的账本不可解绑。
- 报表/预算快照/资产快照为**捕获式冗余**（capturedAt + sourceVersion），是离线展示与同步的基础。
- 业务校验集中在仓储层：余额不足（insufficientFunds）、信用额度超限（creditCardLimitExceeded）、转账账户合法性等 26 个错误码。

### 1.4 数据层与同步

- Drift（SQLite），余额**落库存储**（balanceMinor），非信用账户直接增减；信用类以 postedDebtMinor/frozenCreditMinor 为真变量，balanceMinor 为派生值；写入经内存账本 `_MutableAccountLedger` 校验后落库。
- 预算已用额每次**实时 SQL 求和**（仅 legacy_snapshot 读存储值），交易写后刷新预算快照（upsert + 关旧 open 快照 + autoRollover）。
- 使用统计（建议词）5 张表全量重扫重建，失败静默。
- 同步：`sync_change_logs` 变更日志 + 设备游标（sequence=微秒时间戳）+ DeltaPackage（AES-256-GCM + PBKDF2 210k 迭代）+ 版本冲突检测（baseVersion vs 本地 version）+ 冲突人工解决（交易字段级合并，transfer/ledger/split/installment 组不支持远端采纳）。
- 通知：flutter_local_notifications 本地定时（预算提醒、账单提醒、每日 20:00 汇总 digest）。

### 1.5 小程序化关键约束（难点清单）

1. **本地库过大**：约 55 表、单表多索引，wx 本地缓存单 key 上限 10MB（旧版 1MB），需重新设计存储。
2. **加密落差**：App 依赖 Keychain/Keystore + PBKDF2/AES-GCM；小程序无系统级安全存储，财务数据需纯 JS 加密方案，PBKDF2 210k 迭代在低端机有性能风险。
3. **认证模型**：本地邮箱+密码 → 微信 openid + 可选本地 PIN；App Lock/敏感模块 TTL 二次验证机制需重新设计（小程序生命周期短）。
4. **通知不可移植**：本地调度 → 微信订阅消息（一次性/长期，需要服务端触发，且订阅次数受限）。
5. **WebDAV 直连不可行**：小程序网络层不支持 MKCOL/PROPFIND 等动词 + 域名白名单；与 App 互通需自建中转后端，或降级为加密快照导出/导入（miji.snapshot.v1 信封格式可复用）。
6. **图表/日历**：fl_chart/table_calendar 不可用，需换 echarts-for-weixin 或 canvas 自绘。
7. **时区数据**：timezone 全量数据包不可打包，定时计算需服务端时间或简化。
8. **代码不可复用**：Riverpod/GoRouter/Drift 生成产物作废；可移植蓝本 = money_*_entity 领域模型 + MoneyRepository 接口语义 + 聚合算法（统计/预算/异常检测/现金流）。

## 2. 小程序目标与定位

### 2.1 定位

「米记记账」微信小程序：**记账核心功能的轻量移动端**。目标是让用户在微信内完成 90% 高频记账场景（支出/收入/转账、流水、统计、预算），与 App 数据互通策略见 5.6。

### 2.2 产品原则

- 记账 < 3 秒完成（模板记忆 + 建议补全 + 默认值）
- 离线可用，弱网不丢账
- 隐私优先：财务数据本地加密，默认不上传
- MVP 先保核心链路，不复制全部 8 个分区

### 2.3 范围分级总览

| 级别 | 内容 | 定位 |
|---|---|---|
| P0（MVP） | 账户、记账（收支/转账）、流水、分类、基础统计、基础预算、账本切换、金额格式化/币种 | 首发 |
| P1 | 分期、自动记账、账单提醒+提醒中心、退款、标签、支出异常检测、现金流预测、周期报表、金额隐藏 | 二期 |
| P2 | 家庭账本/成员/分账、预算子分配、分账规则、WebDAV/云同步、与 App 数据互通、多币种账户 | 三期/远期 |

## 3. 需求规格（P0 详细）

### 3.1 全局

- **启动**：授权登录（openid）→ 本地初始化（账户/分类种子）→ 首页=记账页。
- **金额输入**：数字键盘 + 逗号容错，int 分单位存储，按 `defaultMoneyCurrencyCode`（默认 CNY）格式化显示。
- **默认账本**：本地首建个人账本，账本选择器置于记账页顶部。
- **错误提示**：复用 26 个业务错误码的中文文案表（余额不足/额度超限/账户选择无效等）。

### 3.2 记账（核心）

**支出/收入表单**：
- 必填：金额、账户、分类
- 可选：子分类、支付方式（13 种内置 + 自定义名，建议按使用频率排序）、商家/地点/备注、标签、时间（默认当前，可改）
- 交互：分类两级弹层选择；支付方式与商家自动补全（本地最近使用 top8/top6）；收入禁止选信用类账户（沿用现有规则）
- 默认记忆：上次使用的账户/分类/支付方式（对应 App 的 transaction_entry_defaults_store）

**转账表单**：转出账户、转入账户、金额、备注、子分类可选；转出/转入账户候选过滤（排除不可转账类型）。

**流水页**：
- 列表：时间倒序分页（每页 20），卡片显示金额/分类/账户/支付方式/备注
- 筛选：类型、账户、分类、支付方式、日期范围、关键词（备注/商家）
- 详情：点击弹出详情，可编辑/删除/退款（P1）
- 快捷：长按/滑动快捷编辑删除

### 3.3 账户

- 列表按资产类/信用类/负债类分组展示；信用类显示可用额度（余额语义反转），其余显示余额
- 新增/编辑：名称、类型（17 种）、期初余额、币种（默认 CNY）、颜色图标；信用卡额外：额度/账单日/还款日/还款提醒开关
- 停用（不删历史）、软删除可恢复（P1 恢复入口）

### 3.4 分类

- 两级管理：内置种子分类（沿用 `money_seed_data.dart` 全量种子数据）+ 自定义增删改、软删除
- 支出/收入双向切换；首页分类选择器即此数据源

### 3.5 统计（基础版）

- 周期：本月/本周/上月/近三月/今年/自定义（≤93 天按日、否则按月）
- 卡片：收支总览（收入/支出/净额/笔数）、趋势图、分类占比 Top10（环形图）、支付方式占比、账户分布
- 环比：上一周期对比（P0 可只做金额文字对比）

### 3.6 预算（基础版）

- 创建：名称、类型（支出限额/收入目标）、周期（日/周/月/年，P0 不做账单周期）、作用域（全局/分类/账户）、金额、预警阈值、开关
- 列表：进度条（已用/剩余）、超支状态、预警提示
- 交易写入后实时更新已用额（本地 SQL 聚合，同 App 口径）

### 3.7 非功能需求

| 项 | 要求 |
|---|---|
| 包体积 | 首包 ≤ 1.5MB（不含分包），主包+分包 ≤ 8MB |
| 性能 | 记账页冷启动 ≤ 2s；5000 条流水内列表滚动流畅；统计聚合 ≤ 1s（本地） |
| 离线 | 全功能离线可用；启动静默尝试同步（如有） |
| 存储 | 本地 key 分片（按月交易分片 + 摘要表），单 key < 1MB；余额/分类/预算全量快照 |
| 安全 | 财务数据加密落盘（见 5.2）；无明文金额日志；禁止 console 输出金额 |
| 合规 | 隐私协议弹窗；用户可导出/删除全部数据；不采集位置等敏感权限 |
| 兼容 | 基础库 ≥ 2.30（iOS/Android 同构），深色模式自适应 |

## 4. 技术选型：Taro vs 微信原生

### 4.1 对比

| 维度 | 微信原生（WXML/WXSS/TS） | Taro 3/4（React/Vue → 微信） |
|---|---|---|
| 上手曲线 | 需学 WXML/WXSS/组件生命周期；**无框架编译层，调试链路最短** | React/Vue 心智；熟悉 JS 团队上手快；需理解编译差异 |
| 微信能力集成 | 原生支持最完整（订阅消息、隐私、分享、加密、storage） | 大多可透传，但能力升级有适配滞后，部分需写原生插件 |
| 性能 | 最佳（无中间层），复杂列表/长列表可控 | 有运行时适配层损耗，Taro 3 为动态化渲染，长列表/重交互需优化 |
| 包体积 | 最小 | 引入框架 runtime（约 +100~300KB） |
| 多端能力 | 仅微信；改支付宝/抖音需重写 | 一套代码可出微信/支付宝/抖音/H5/RN |
| 生态 | 官方组件/插件直接可用 | 用 React 生态组件，echarts 等有现成 Taro 封装 |
| 类型/工程 | TS 原生支持，miniprogram 官方工具链 | TS 一等公民，CLI 工程化成熟（构建/热更新） |
| 与现有 Flutter/Dart 资产 | 无复用（两边都是全新），但**领域模型/算法可以语言无关方式平移** | 同样无直接复用 |
| 长期风险 | 微信平台绑定；WXML 表达能力弱（复杂动画/布局需 wxs 补） | 框架版本碎片化、升级破坏性；微信底层变化时适配慢 |

### 4.2 本项目特殊考量

1. **记账业务复杂度高**：复杂表单（两级分类、支付方式建议、分账）、长列表分页、图表多、聚合计算多。两者都能做，但**原生在列表滚动与键盘输入场景更稳**。
2. **团队技能栈**：现有团队是 Dart/Flutter；若无 React 经验，「原生 WXML + TS」的学习曲线反而更短（无框架心智 + 官方文档最全）。
3. **微信深度依赖**：订阅消息（提醒替代方案）、openid 认证、隐私合规（财务数据敏感）——原生集成最直接，无框架适配风险。
4. **多端诉求**：记账类工具短期内无支付宝/抖音多端刚需；若未来要做 H5 版，原生版可单独抽壳，但 Taro 更顺。
5. **图表**：两者都用 echarts-for-weixin（原生）或 taro-echarts，无显著差异。
6. **排期确定性**：原生无编译层黑盒，出问题可定位到微信开发者工具底层，适合 MVP 快速交付。

### 4.3 结论（建议）

> **推荐：微信原生（TypeScript + 原生组件框架，采用自定义组件/分包架构）作为 P0 技术栈。**

理由：单一平台目标 + 微信能力深度耦合 + 团队无 React 经验 + 财务类 App 对稳定性/性能/隐私合规要求高 + MVP 交付节奏。**建议同时采用**：
- **代码组织借鉴 Taro 的工程化思想**（模块分包、TS 严格模式、DTO 与领域模型分层），不引入框架。
- 若后续明确要覆盖支付宝/抖音/H5 多端，**预留重构边界**：所有业务逻辑（记账/统计/预算算法）与平台无关地放入 `src/core` + `src/features` 纯 TS 层，UI 层薄化——届时迁移 Taro 只需重写 UI 层（约 30% 工作量）。

**条件性替代**：若团队已有 React 经验且确认半年内要出 H5/多端，可选 Taro（React）+ taro-echarts + zustand/jotai；否则不建议为框架引入不确定性。

## 5. 技术方案概要

### 5.1 总体架构

```
src/
├── app/            # App 入口、全局配置、隐私协议
├── core/
│   ├── storage/    # 本地存储引擎（分片 + 加密 + 事务）
│   ├── sync/       # 同步/导出导入（P2 预留）
│   ├── security/   # PBKDF2/AES-GCM 纯 JS 实现
│   ├── utils/      # 金额格式化、时间区间、错误码映射
│   └── ui/         # 通用组件（金额键盘、卡片、空态、弹层）
├── features/
│   ├── auth/       # openid 登录、本地 PIN（P1）
│   ├── ledger/     # 账本选择
│   ├── accounts/   # 账户
│   ├── transactions/# 记账/转账/流水
│   ├── categories/ # 分类
│   ├── statistics/ # 统计
│   └── budgets/    # 预算
├── data/
│   ├── schema/     # 本地表结构与迁移
│   ├── seed/       # 种子分类/币种（从 money_seed_data.dart 平移）
│   └── repository/ # 仓储（对应 MoneyRepository 接口语义）
└── pages/          # 页面注册（分包 pages-account/...）
```

### 5.2 本地存储方案（关键决策）

- **不用单 key JSON 堆大对象**。方案：**按月分片 + 摘要表**：
  - `txn_YYYYMM`（当月流水，单 key）、`txn_index`（索引：id→(月,时间)，用于跨月查询）、`txn_summary_YYYYMM`（按月分类/账户/支付方式聚合摘要，供统计首屏与跨月快速聚合）
  - `accounts`、`categories`、`budgets`、`ledgers` 等小表全量单 key（含 version/isDeleted）
- **写入协议**：单交易写入 = 更新流水片 + 摘要 + 账户余额 + 预算已用，用「先写变更日志（append-only）→ 幂等重放」保证一致性（借鉴 App 的 sync_change_logs 思路，用 `last_seq` 快照标记落库进度）。
- **加密**：敏感字段（金额、备注、商户）值级加密：PBKDF2（迭代降至 10k~20k 平衡性能）+ AES-GCM，密钥存 `wx.setStorage` 本地，加盐；开启「隐私模式」时全量加密（P1）。
- **容量**：单 key 限 1MB 内；>10 万条流水时启用归档（历史片离线导出）。

### 5.3 状态管理

- 原生 + TS 下推荐 **轻量分层**：`repository（单例）→ service/notifier（页面级 store，手写发布订阅或用 `mobx-miniprogram`）→ 页面 setData`。
- 建议 P0 用纯 TS 手写 store（约 5 个），避免引入 mobx 依赖；P1 若组件树复杂再评估 mobx-miniprogram。
- 关键：金额/聚合计算全部在 service 层完成，页面只做渲染，保证可单测（vitest/jest + 纯逻辑层）。

### 5.4 图表与 UI

- 图表：echarts-for-weixin（分包独立，仅统计页加载）；P0 用 canvas 自绘简版柱/环图可先顶替。
- 记账键盘：自定义 number keyboard（仿随手记/微信支付键盘），避免原生输入框聚焦问题。
- 列表：recycle-view（官方扩展库）用于流水长列表。
- 主题：CSS 变量 + 深浅色（`darkmode` 媒体查询）。

### 5.5 通知与提醒（P1）

- 微信订阅消息：一次性订阅为主（用户记账后引导订阅「还款提醒」「预算预警」）；长期订阅仅部分类目可用。
- **架构**：小程序端生成本地待办列表（提醒中心）+ 可选**轻量云函数**定时触发订阅消息（需要开通云开发，P1 评估）。纯本地无法实现 App 级定时提醒，需明确降级预期（打开小程序可见提醒中心红点）。

### 5.6 数据互通与同步策略（P2，但需 P0 预留）

- **推荐路径 A（P0 预留，成本最低）**：加密快照导出/导入，复用 App 的 `miji.snapshot.v1` 信封格式（PBKDF2 210k + AES-256-GCM）。小程序端解析 App 导出文件初始化本地库；小程序「导出备份」文件可被 App 恢复。**兼容重点：JSON 字段命名与 App 的 toJson/fromJson 一致。**
- **路径 B（远期）**：自建中转服务（云开发云函数或自建 Node 服务），桥接 delta 协议（datasetId/deviceId/sequence/cursor/conflict）。需复刻 DeltaPackage 加解密与冲突模型，工作量大，三期再议。
- P0 即要求：本地存储字段命名/枚举值/分单位与 App 完全一致（直接以 App 实体字段为 schema 蓝本）。
