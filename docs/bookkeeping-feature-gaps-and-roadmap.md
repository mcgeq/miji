# 记账模块功能缺口分析与落地方案

> 分析日期：2026-10-11  
> 范围：`lib/features/bookkeeping/` 全部 + `core/database/`、`core/sync/`、`features/settings/` 相关部分  
> 说明：本文只做分析，不涉及代码改动。行号为分析时快照，定位请以函数名 / 代码片段为准。  
> 上一篇（UI / 布局）见 `docs/bookkeeping-ui-ux-review.md`，两者互补：那篇解决「已有的东西怎么摆」，本篇解决「缺的东西怎么补」。

## 一、结论速览

记账模块的**基础盘很扎实**：16 类账户、三级分类、预算（含分配/历史/未来义务预留）、三种计息的分期、定时自动记账、账单提醒 + 提醒中心、家庭账本与成员分摊、22 张统计卡片、CSV 导出。这套东西已经超过绝大多数个人记账 App 的**手工记账**能力。

但它&#x5728;**「把外面世界的账弄进来」**&#x8FD9;件事上几乎是空白：

| # | 缺口                          | 本质                     |
| - | --------------------------- | ---------------------- |
| 1 | **账单导入**（支付宝 / 微信 / 银行 CSV） | 用户已经有一堆现成流水，却只能一条条手敲   |
| 2 | **图片识别记账**（截图 / 小票 OCR）     | 付款完成到记账之间隔着一次手动录入      |
| 3 | ~~**支付通知捕获**（监听支付宝/微信通知自动落账）~~ | **已排除**（见 5.5）；用户决定不申请通知读取权限 |
| 4 | 流水**来源与外部单号**字段缺失           | 导入的地基：没有它，重复导入无法去重     |
| 5 | **附件 / 小票存储**能力没有（只落了通用目录层） | 图片识别、发票、凭证都要它          |
| 6 | **分类规则引擎**（按商家/关键词自动填分类）    | 导入 3000 条后全是「未分类」，等于没导 |

一句话判断：**现在的记账模块是一台很好的「手工录入机」，缺的是「入口」和「自动化」。** 下面所有方案都围绕这两件事。

## 二、先决条件：四个绕不开的硬约束

方案能不能落地，先看这四条。它们不是建议，是既成事实，直接决定了技术选型的边界。

### 2.1 这是一个纯本地、离线优先的单机 App

- App 内**没有任何服务端**、没有账号体系。唯一的网络能力是用户自配 WebDAV 做设备间同步（`core/sync/webdav/`）。
- 全项目搜不到任何 LLM / 开放 API 调用；`dio` 只被 `webdav_client.dart` 一个文件使用，且是 WebDAV 专用 client（Basic Auth、无拦截器、无统一错误映射）。
- `flutter_secure_storage` 已有成熟用法（键名 `floating.dotted`，如 `sync.webdav.config`），可以承载「用户自带 Key」。

> **推论**：任何云端能力（云 OCR、多模态大模型）都必须是**用户自带 Key**，App 不提供也不垫付。想做成「开箱即用」就必须走端侧。

### 2.2 五个平台：Android / iOS / macOS / Windows / Web

`android / ios / macos / web / windows` 五个平台目录都在，`flutter_launcher_icons` 也为这五个平台生成了图标。

> **推论**：`google_mlkit_*` 系列只有 Android/iOS 实现，**桌面与 Web 不可用**。跨平台方案要么做能力降级，要么选纯 Dart 实现。

### 2.3 没有附件 / 文件基础设施

- 没有「把文件收进 App 私有目录 + 记录引用」的通用能力，现有落盘都是各页面就地写：
  - 头像：`settings_page.dart:796-858`（`getApplicationSupportDirectory()/avatars` + `XFile.saveTo`）
  - CSV 导出：`money_transactions_section.dart:983-989`（写临时目录 + `SharePlus`）
- **GTD 打卡照片的隐患已修**（原本 `drift_checkin_repository.dart:472-495` 把 `image_picker` 返回的**临时路径**原样写进 `checkin_photos.local_path`，临时目录被系统清理后照片必失效）。现在 `addPhoto` 先把文件收进统一附件目录、库里只存相对路径；读取侧由 `_photoFromRow` 统一解析回绝对路径，历史行里存的绝对路径原样放行，老照片不会读废。

### 2.4 新增一张数据表要手工接 6 处

| 步骤          | 位置                                                                                                                                                                                                            |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. 定义 Table | `core/database/tables/money/xxx_tables.dart`（新建）                                                                                                                                                              |
| 2. 注册       | `app_database.dart:30-88` `@DriftDatabase(tables: [...])`                                                                                                                                                     |
| 3. 版本自增     | `app_database.dart:102` `schemaVersion`（当前 **24**）                                                                                                                                                            |
| 4. 迁移       | `app_database.dart:105-312` `onUpgrade` 加 `if (from < N)`                                                                                                                                                     |
| 5. 重新生成     | `build_runner build`（`app_database.g.dart`）                                                                                                                                                                   |
| 6. 接入同步     | `sync_change_logger.dart` 表名常量 + `recordXxxChange`、`drift_money_repository.dart` 转发、写路径显式调用、`parts/remote_apply.dart` switch 分支、`delta_sync_service.dart` 的 `readLocalRecord` 分派与 `_isSupportedMoneyTable` 名单 |

迁移测试在 `test/core/database/app_database_migration_test.dart`（用「建当前 schema → 手工 DROP → 回退 user_version」伪造旧库）。

> **推论**：新表成本不低（尤其第 6 步，同步没有统一的自动钩子）。方案要**尽量复用现有表**——优先用已有的 `notes` / `merchant` / `location`，能加列就不开表。

### 2.5 其它

- **`file_picker` 未引入**（pubspec 无此依赖，代码里也没有 `FilePicker`）。账单导入必须先补。
- **Dart 无内置 GBK 解码**，而支付宝个人账单恰恰是 GBK 编码（见 5.3）。
- **完全硬编码中文**，无 l10n（无 `.arb`、无 `AppLocalizations`）。新功能跟随现状即可，不必为此立项。

按「一笔钱从发生到被看懂」的路径分五层：

| 层        | 已有                                                                                           | 缺                                    |
| -------- | -------------------------------------------------------------------------------------------- | ------------------------------------ |
| **① 录入** | 手动记一笔（含算式输入 + 计算器 + 常用分类 + 历史商户建议 + 记住上次选择 + 保存并继续 + 再来一笔）、转账、定时自动记账模板、分期到期入账、提醒跳转记账、通知点击进记账 | 账单导入、图片识别、语音、分享目标、桌面快捷方式 |

| **③ 核对** | 账户余额校正、退款/作废、待处理状态、分期状态修复、自动记账冲突接管                                                           | 外部单号去重、账户余额对账、报销标记、应收应付              |
| **④ 凭证** | 无（附件目录能力已具备，目前仅 GTD 打卡照片在用） | 附件表、小票/发票查看、流水凭证 |
| **⑤ 洞察** | 22 张统计卡（趋势/环比/异常/排行/渠道/时段/预算/净值/未来现金流/成员参与）、本地「分析报表」（周/月/季/年）、预算未来义务预留                       | 自动预算建议、储蓄目标、真正的 AI 文字报表              |
| **⑥ 协作** | 家庭账本 + 本地成员 + 分摊规则/记录、WebDAV 设备间同步                                                           | 在线多人协作（与「无后端」定位冲突）                   |

补充事实（几处容易误判的）：

- 统计页的 **「AI 报表」卡实际是纯本地聚合**（`data/parts/reports.dart:83-171`），只算收入/支出/净额/分类 Top/商家 Top/分期与自动记账占比/预算使用率，**没有任何模型调用**。叫「AI」是名不副实。
- **「重复」这个词在当前代码里是「再来一笔」**（`money_transaction_actions.dart:142-194` 复制成新单），不是去重检测。真正的重复检测只有「自动记账模板 ↔ 分期计划」之间的引擎级冲突（`auto_posting_conflicts.dart`），与用户流水无关。
- **流水来源是隐式派生的**：自动记账看 `sourceTemplateRunId`，分期看 `installmentPlanId`，其余算「其他」。没有显式字段，也没有「导入」这个来源。
- 「记账偏好」设置页只有「默认币种 + 提醒通知」两项，很轻。

## 五、重点方案

### 5.1 地基 A：流水来源与外部单号（G1）

**为什么必须先做**：账单导入最大的风险是**重复导入**。用户第一周导了一次，第二周又导一次（时间范围重叠），如果没有稳定去重键，就会凭空多出几百笔账。支付宝/微信账单里天然带全局唯一单号，用它做去重键是唯一可靠的办法。

**改动**：

1. `MoneyTransactions` 表加三列：
   - `source`（TEXT，非空，默认 `manual`）：枚举 `manual / import / ocr / notification / autoPosting / installment / transfer`
   - `externalId`（TEXT，可空）：形如 `alipay:<交易订单号>` / `wechat:<交易单号>` / `bank:<单号>`，带来源前缀避免跨平台撞号
   - `importBatchId`（TEXT，可空）：导入批次，用于整批回滚
2. 加**部分唯一索引** `(user_id, external_id) WHERE external_id IS NOT NULL`——SQLite 的部分索引项目里已有先例（`money_currency_tables.dart` 的分类表就用了带 WHERE 的唯一索引）。
3. 迁移 `schemaVersion` 24 → 25；历史数据 `source` 一律回填 `manual`（分期/自动记账的历史行可选择性按 `installmentPlanId` / `sourceTemplateRunId` 回填，非必须）。
4. 同步：三列要进 `changedFields`，按 2.4 第 6 步的清单登记（外部单号参与同步是必要的，否则两台设备导入同一份账单会各存一份、去重失效）。
5. 统计页「来源拆解」卡（`money_source_breakdown_card.dart`）改为读 `source` 字段，旧派生逻辑保留为历史数据兜底。

**成本**：小。**收益**：去重、归因、批次回滚三件事一次到位，且以后每加一个自动录入通道（OCR/通知）都直接受益。

### 5.2 地基 B：通用附件存储（G2）

**目标**：一个「把外部文件收进 App 私有目录、并能在需要时读回来」的通用能力。

**原设计**（实际落地情况见本节末）：

```
lib/core/attachments/
  attachment_store.dart      # 落盘 / 读取 / 删除 / 孤儿清理
  attachment_paths.dart      # 目录规则 + 相对路径解析
```

- 目录：`getApplicationSupportDirectory()/attachments/<userId>/<yyyyMM>/<uuid>.<ext>`
- **存相对路径不存绝对路径**：iOS 沙盒路径每次升级都会变，绝对路径必失效（现在 GTD 打卡就踩在类似问题上）。
- 写入要**原子**：先写 `.tmp` 再 `rename`。
- 图片策略：保留原图 + 生成缩略图（长边 256）；列表页用缩略图，详情页才读原图。避免一屏流水把几张 4MB 的图全解进内存。
- 删除策略：**标记 + 延迟清理**。流水进回收站时附件保留，真正硬删或回收站清空时才删文件，并且用「引用计数 / 定期扫孤儿」兜底（避免删除流水后文件残留）。

**原方案的新表**：`MoneyTransactionAttachments`（**未采用**，见下）

| 列                          | 说明                                                                             |
| -------------------------- | ------------------------------------------------------------------------------ |
| `id`                       | 主键                                                                             |
| `userId` / `transactionId` | 归属 + 关联流水                                                                      |
| `relativePath`             | 相对 `attachments/` 的路径                                                          |
| `mimeType` / `byteSize`    | 类型与体积                                                                          |
| `kind`                     | `receipt`（小票）/ `screenshot`（支付截图）/ `invoice`（发票）                               |
| `ocrText`                  | OCR 原始文本（可选，存下来便于重解析与排查）                                                       |
| 同步列                        | `deviceId` / `version` / `isDeleted` / `deletedAt` / `createdAt` / `updatedAt` |

**关于附件是否参与 WebDAV 同步**：**不参与**（第七节决策 2 已拍板）。二进制进 delta 包会把同步体积放大几个数量级，而现有 delta 包是「逐条 JSON 变更」的设计（`delta_package_models.dart`），不适配大文件。
> 佐证：`checkin_photos` 那张同样存文件的表，`SyncChangeLogger` 里写了 `recordCheckinPhotoChange`，但**从没有任何地方调用它**——登记白写。文件类数据就别往 delta 同步里塞。

**落地情况（V1.7）**：只落地了**存储层**，记账侧的凭证部分随后被撤掉。

| 件 | 状态 | 位置 / 说明 |
|---|---|---|
| 路径规则 | ✅ 已落地 | `lib/core/attachments/attachment_paths.dart`（纯 Dart，无 `dart:io`，可单测）：`<userId>/<yyyyMM>/<id>.<ext>`，分隔符固定 `/`，目录名做非法字符清洗挡穿越 |
| 存储层 | ✅ 已落地 | `lib/core/attachments/attachment_store.dart`：原子拷贝（`.tmp` → `rename`）、相对↔绝对解析、删除；根目录注入点便于单测 |
| 首个调用方 | ✅ GTD 打卡照片 | 见 §2.3，顺带修掉了那里的临时路径隐患 |
| `MoneyTransactionAttachments` 表 | ❌ 未采用 | 曾在 `schemaVersion` 25 上建过，已整体撤回，库版本仍是 24 |
| 截图落库 / 详情页凭证区 | ❌ 未采用 | 用户决定「识别的图片不作为附件保留」 |

**为什么记账侧不做**：附件只在真有「文件本体」要留时才有意义。用户明确不要保存识别用的截图，小票/发票的采集入口也一直没做，那么表、仓库、详情页凭证区都会是没有数据来源的空壳。存储层留下是因为它本身通用（GTD 打卡照片立刻用上，也顺手修掉了那里的隐患）。

**缩略图策略**暂不需要：目前唯一的调用方是打卡照片，量级远没到「一屏几百张图」的地步。真要做凭证时再补（长边 256 + 列表用缩略图、详情页读原图）。

### 5.3 方案 ①：支付宝 / 微信账单导入（G4）

#### 5.3.1 先看清账单长什么样

两份账单的格式差异比想象中大，且**同一个平台还不止一种格式**：

**支付宝 · App「开具交易流水证明 → 用于个人对账」**

- 编码：**GBK**（不是 UTF-8）
- 结构：**前 24 行**是说明信息，**第 25 行**是表头
- 列：`交易时间, 交易分类, 交易对方, 对方账号, 商品说明, 收/支, 金额, 收/付款方式, 交易状态, 交易订单号, 商家订单号, 备注`
- 金额为纯数字；最底有汇总行
- 文件是邮件附件里的**加密压缩包**，解压密码要在 App 内「开具记录」里查

**支付宝 · 网页版「服务大厅 → 自助服务 → 交易记录」导出**

- 结构：**前 4 行**说明
- **16 列**，且列名不同：`交易号, 商家订单号, 交易创建时间, 付款时间, 最近修改时间, 交易来源地, 类型, 交易对方, 商品名称, 金额(元), 收/支, 交易状态, 服务费(元), 成功退款(元), 备注, 资金状态`

**微信 · 「账单 → 常见问题 → 下载账单 → 用于个人对账」**

- 编码：**UTF-8**（带 BOM）
- 结构：**前 16 行**说明，**第 17 行**表头，第 18 行起数据
- 列：`交易时间, 交易类型, 交易对方, 商品, 收/支, 金额(元), 支付方式, 当前状态, 交易单号, 商户单号, 备注`（注意「金额(元)」和「支付方式」前有空格）
- 金额带 `¥` 前缀，如 `¥6.00`
- `收/支` 是**三态**：`收入` / `支出` / **`不计收支`**
- 尾部有 `----------------------微信支付账单明细列表--------------------` 分隔行 + 「共 N 笔记录」等汇总行

> ⚠️ **格式选择建议写进 UI 文案**：微信「用做证明材料」导出的是**带公章 PDF**，无法解析；支付宝同理。必须在引导页明确写「请选择**用于个人对账**」。这是这类功能最高频的用户求助点。

#### 5.3.2 关键设计原则：**按表头名映射，不按列下标**

因为支付宝自己就有 12 列和 16 列两套、说明行数也不一样，任何「跳过 N 行、取第 M 列」的硬编码都会在版本差异下碎掉。

正确做法（数据驱动解析）：

1. **编码嗅探**：先看 UTF-8 BOM → 试 UTF-8 严格解码 → 失败回退 GBK → 都失败则报「无法识别编码，请另存为 UTF-8」。
2. **表头定位**：逐行扫描，找**同时包含「交易时间」和「收/支」**&#x7684;那一行作为表头行（不信任固定的第 25 行 / 第 17 行）。
3. **列名归一**：建一张别名表，把各平台列名归一到内部字段。
4. **数据行判定**：首列能解析成日期才算数据行，否则丢弃（自动过滤尾部汇总行、分隔行、空行、支付宝的说明行）。
5. **平台识别**：由表头列名反推（有「交易单号」= 微信；有「交易订单号」/「交易号」= 支付宝），用户不必手选平台——但保留手动覆盖开关。

列名 → 内部字段的归一表：

| 内部字段  | 支付宝（App） | 支付宝（网页）       | 微信                         |
| ----- | -------- | ------------- | -------------------------- |
| 时间    | 交易时间     | 付款时间 / 交易创建时间 | 交易时间                       |
| 对方    | 交易对方     | 交易对方          | 交易对方                       |
| 商品/摘要 | 商品说明     | 商品名称          | 商品                         |
| 收支方向  | 收/支      | 收/支           | 收/支（三态）                    |
| 金额    | 金额       | 金额(元)         | 金额(元)（带 `¥`）               |
| 渠道    | 收/付款方式   | （无）           | 支付方式                       |
| 状态    | 交易状态     | 交易状态          | 当前状态                       |
| 外部单号  | 交易订单号    | 交易号           | 交易单号                       |
| 商家单号  | 商家订单号    | 商家订单号         | 商户单号                       |
| 平台分类  | 交易分类     | 类型            | 交易类型                       |
| 退款    | —        | 成功退款(元)       | （在「当前状态」里，如 `已退款(¥12.00)`） |
| 备注    | 备注       | 备注            | 备注                         |

#### 5.3.3 GBK 怎么解（这是最硬的技术点）

Dart 没有内置 GBK。三个选项：

| 方案                  | 说明                                                       | 评价                  |
| ------------------- | -------------------------------------------------------- | ------------------- |
| `charset_converter` | 走平台原生（Android/iOS/macOS 有实现，Web 有 JS 兜底），**Windows 需实测** | 依赖面最广，但要验 Windows   |
| `fast_gbk`          | 纯 Dart，体积小                                               | 覆盖率是 GBK 子集，冷僻字可能出错 |
| 内嵌映射表               | 自己带 GBK→Unicode 表（约 2 万条，~200KB 资源）                      | 零依赖、五端一致、完全可控，但要自己写 |

**建议**：先做**方案排序自动降级**——优先 `charset_converter`，不可用时提示用户「请用记事本另存为 UTF-8 再导入」。若实测 Windows 有问题，直接上内嵌映射表（一劳永逸，且这个表以后解析其它国产系统导出的文件也用得上）。**不建议在第一步就引原生插件**，因为它会同时影响五端构建。

> 另有一个更省事的备选：引导用户**在 Excel/Numbers 里把支付宝账单另存为 UTF-8 CSV** 再导入。可作为首版的降级路径，把 GBK 支持延后。

#### 5.3.4 「不计收支」怎么落（产品决策点）

微信的「不计收支」覆盖的是：**充值、提现、零钱通/理财通存取、信用卡还款**。这些在语义上**绝大多数就是本项目的「转账」**：

- 信用卡还款 = 储蓄卡 → 信用卡（本项目 `transfer` 会成对生成两行，并正确改变信用卡可用额度）
- 提现 = 零钱 → 银行卡
- 充值 = 银行卡 → 零钱
- 零钱通存取 = 零钱 ↔ 零钱通

这是**很漂亮的对齐**：如果把信用卡还款当支出导入，用户的支出会被虚增（还款不是消费）；当转账导入则正好。

**建议映射**：

| 账单方向 | 映射为                                | 说明                      |
| ---- | ---------------------------------- | ----------------------- |
| 支出   | `type=expense`，`status=completed`  | 正常计支出                   |
| 收入   | `type=income`，`status=completed`   | 正常计收入                   |
| 不计收支 | `type=transfer` + `status=pending` | **落为待处理**，让用户在预览页指定对手账户 |


之所以落 `pending`：账单里只有「收/付款方式」一列，**推不出对手账户**（「工商银行8888」是付款方，但收款方（信用卡）是谁不知道）。项目现有的 `pending` 状态语义刚好完美契合——**不计入余额、不计入统计**，正好是「这笔钱不该算消费」，等用户补上对手账户再确认。这套「先落草稿 → 用户确认」的模式，项目在自动记账（run 的 `pending` 状态）和提醒中心里已经在用了。

#### 5.3.5 渠道名 → 本地账户的映射

账单里的渠道是自由文本：「工商银行8888」「招商银行信用卡(1234)」「零钱」「零钱通」「余额宝」「花呗」。

**策略**：首次导入时进入「渠道绑定」步骤，列出账单里出现的所有渠道名 + 出现次数 + 金额合计，让用户逐个绑定到本地账户；绑定结果持久化（SharedPreferences，按 userId）。下次导入自动套用，用户可编辑。

- 匹配不上的渠道 → 落到一个用户指定的「默认导入账户」。
- 支付宝「余额宝」/ 微信「零钱通」这类**本质是货币基金而非钱包**的渠道，建议允许绑定到「投资」类账户。
- 账单里的「花呗」应绑定到 `huabei` 类型账户，这样导入后花呗欠款视图能对上。

#### 5.3.6 状态映射与退款

**微信「当前状态」**：`支付成功` / `已转账` / `已收钱` / `已存入零钱` / `提现已到账` / `已全额退款` / `已退款(¥xx)` / `对方已退还` / `支付失败`

**支付宝「交易状态」**：`交易成功` / `退款成功` / `交易关闭` / `已关闭` / `等待付款`

映射规则：

- 正常成功 → `completed`
- 「已退款(¥xx)」→ 解析金额填入 `refundAmountMinor`，状态仍 `completed`（项目已有 `refundAmountMinor` 字段和 `recordTransactionRefund` 方法，统计页也有退款汇总卡）
- 「已全额退款」→ `refundAmountMinor = amountMinor`
- 「支付失败 / 交易关闭 / 已关闭」→ **不导入**（在预览页归入「已跳过」并给出原因）
- 「等待付款」→ `pending`

#### 5.3.7 分类映射

- 支付宝「交易分类」（如「餐饮美食」「交通出行」「服饰装扮」）与微信「交易类型」（如「商户消费」「扫二维码付款」「转账」「红包」）→ 映射到本地分类。
- 微信的「交易类型」偏向**支付方式**而非消费类别（「扫二维码付款」不是分类），映射价值低，建议**不作为分类依据，而是作为 `paymentMethod` 的参考**。
- 支付宝的「交易分类」质量较高，可直接映射。
- 映射表**持久化且用户可编辑**；首版可以先给一张内置默认映射（对齐 `core/database/seed/money_seed_data.dart` 的内置分类名）。
- 映射不上的 → 交给 5.6 的分类规则引擎 → 再不上就落「未分类」，用已有的批量修改功能统一收拾。

#### 5.3.8 导入流程与 UI

```
流水页「⋯」菜单 → 导入账单
   ↓
① 选文件（file_picker，多选；Web 端走 HTML input）
   ↓
② 解析 + 预览
     · 顶部统计：共 N 笔 · 将导入 M 笔 · 重复 K 笔 · 跳过 J 笔
     · 可筛选「只看将导入 / 重复 / 跳过」
     · 每行可勾选、可改分类、可改账户
   ↓
③ 渠道绑定（首次）
   ↓
④ 确认导入 → 事务分批写入（每批 200 条）
   ↓
⑤ 结果页：「已导入 M 笔」+ [撤销本次导入]
```

**入口位置**：建议放**流水页「⋯」菜单**，与已有的「导出流水」（`money_transactions_section.dart:3151`）并列，一进一出对称。同时在**流水页空态**（「还没有流水」那个空态）加一个「从账单导入」按钮——新用户导一次账单，App 立刻从空的变成满的，这是最好的首次体验。

**去重逻辑**：以 `externalId` 为键查库，已存在则归入「重复」组；预览页给「重复项」两个选项——**跳过**（默认）/ **覆盖更新**（用账单里的值刷本地那笔，适合用户手改过账单字段的场景）。

**性能考虑**：一次导入几千条时，注意两件事：

1. **写库分批**：每 200 条一个事务。Drift 的单次超大批量在移动端会卡主 isolate。
2. **同步日志会爆**：delta sync 是「每条写一行 `sync_change_logs`」的设计（`sync_change_logger.dart`）。导入 3000 条 = 3000 行日志 = 下一个 delta 包巨大。建议**导入期间挂起逐条日志，导入结束后统一产生一条「批量导入」变更记录**，或简单点——导入完成后触发一次「整库快照」上传而不是增量。这条要在实现时专门处理，否则会把同步拖垮。

### 5.4 方案 ②：图片识别记账（G5）

#### 5.4.1 先分清两类场景，它们的难度差一个数量级

| 场景                                | 版面                 | 建议手段                       |
| --------------------------------- | ------------------ | -------------------------- |
| **A. 支付成功页截图**（支付宝/微信付款完成那个绿底对勾页） | 极其稳定、字段少、金额字号最大    | **端侧 OCR + 规则抽取就够，不需要大模型** |
| **B. 纸质小票**（超市/餐厅，多行商品、总价、优惠）     | 版面千变万化、有折痕/倾斜/热敏褪色 | 规则不够，需要多模态模型               |

**建议先只做 A**。理由：A 是高频场景（每次扫码付款后截个图就行），且**规则能解**，零 API 成本、零网络依赖、离线可用、准确率可控。B 放到 P2，且依赖 BYO-Key 决策。

#### 5.4.2 端侧 OCR 的平台限制

`google_mlkit_text_recognition` 支持中文（`TextRecognitionScript.chinese`），但**只有 Android / iOS**。

处理方式：

- 用 `defaultTargetPlatform` 做能力检测，桌面/Web **不显示**拍照识别入口（而不是显示了再报错）。
- 把 ML Kit 调用**隔离在单独文件**里，用条件导入（`if (dart.library.io)` 之类）避免其它平台被牵连。
- **必须实测 `flutter build windows` / `macos` / `web` 是否受影响**——ML Kit 系插件在非移动端的行为要验证，这是引入前的前置验证项，不能想当然。

#### 5.4.3 从 OCR 文本到结构化字段

下面是**三张真实截图跑出来的 OCR 文本**（`scriptures/IMG_4561~4563`），分别来自微信、银行 App、支付宝。结论很反直觉：**这三种版式里只有一种带字段标签**，另两种的收款方就是页面大标题。

```
微信账单详情（IMG_4561）
  全部账单
  扫二维码付款-给星空钢琴杨老师     ← 收款方，整行无标签
  -5000.00                          ← 金额：带负号、不带 ¥
  当前状态  支付成功
  收款方备注  二维码收款
  付款方留言  葛奕姝2027学琴费用，明年11月开始
  新学期                            ← 备注折行到这里
  支付方式  零钱通
  转账时间  2026年10月11日08:45:44
  转账单号  100010730120261011016951192775

银行 App 交易详情（IMG_4562）
  交易详情
  未入账
  支付宝-上海壹佰米网络科技有限公司  ← 收款方，整行无标签
  - ￥ 18.40                        ← 三种版式里**唯一带货币符号**的金额行
  交易卡号  信用卡6225********9892
  交易时间  2026-10-1017:46:55      ← OCR 把中间空格丢了
  银行交易类型  消费
  分类  餐饮                        ← 有分类字段
  备注
  记录点什么..                      ← 输入框占位符，不是备注

支付宝账单详情（IMG_4563）
  账单详情
  叮咚买菜>                         ← 收款方，整行无标签
  -18.40                            ← 金额：带负号、不带 ¥
  支付时间  2026-10-10 17:46:56
  付款方式  招商银行信用卡(9892)
  收款方全称  上海壹佰米网络科技有限公司   ← 公司全称，不如标题好用
  账单分类  餐饮美食                 ← 有分类字段
```

**抽取策略（已按实现落地）**：

| 字段 | 做法 |
|---|---|
| **金额** | 三轮降级：① `¥/￥` 符号行 → ② `N 元` → ③ **整行只有金额**（前后各许挂不超过 4 个非数字字符的「装饰」，`- ¥ 18.40`、`- Y 18.40`、`18.40元` 都算）。正负号一起吃掉（`-`/`−`/`–`/`—`/`－`/`+`/`＋`），含 `优惠/立减/折扣/红包/抵扣/积分/余额` 的行整行跳过。③ 那轮**强制要求小数点**——年份、页码、单号片段这些裸整数一律不认；装饰里也不许出现数字（`1000 18.40` 不认）。第 ③ 轮改成「剥掉装饰」而不是「纯数字」，是被真机逼出来的，见 5.4.8。 |
| **商户** | ① **金额行正上方那一行**（三种版式都把收款方摆在那里，比找标签可靠得多）；② 标签兜底。取值时撕掉渠道前缀（`扫二维码付款-给`、`支付宝-`）与展开箭头（`>`），并在噪声词处截断（`…有限公司 未入账`）。 |
| **时间** | `yyyy-MM-dd HH:mm:ss` / `yyyy年MM月dd日HH:mm:ss`；缺失或晚于当前时刻就留空（宁可空着，不填一个错时间）。 |
| **支付方式** | `付款方式` / `支付方式` / `交易卡号` 后的文本 → `MoneyPaymentMethod`。`零钱通` 归 `wechatPay`。 |
| **收支方向** | **金额前的正负号优先**（`-` → 支出，`+` → 收入），没有符号才去找「收款成功 / 已到账」这类关键词。 |
| **分类** | `账单分类` / `分类` 后的文本（只有支付宝和银行 App 有），按**名称**匹配本地分类：先全等，再互相包含（支付宝写「餐饮美食」、本地叫「餐饮」）。匹配不上就留空让用户选，**不硬塞近似分类**——分类错了会连带污染统计占比和预算。 |
| **备注** | `付款方留言` / `备注` 后的文本，并**把折行的续写并回来**（微信的长用途说明常占两行），但撞上下一个字段名就立刻收手。输入框占位符（`记录点什么…`）要挡掉。 |

**两个必须处理的合并行陷阱**（OCR 把左右两列并成一行时才会暴露）：

1. **短标签被长标签包住**——`收款方备注  二维码收款` 里含「备注」，若不加判断就会被当成备注字段，取到「二维码收款」。判据：标签必须落在行首或紧跟在分隔符之后。
2. **同一行的左右两列**——`分类  餐饮`、`交易卡号  信用卡6225…`。取值要支持「同行」与「下一行」两种排布，因为 ML Kit 会不会把两列并成一行并不确定。

**产品原则：OCR 结果一律回填表单让用户确认，绝不自动落账。** 支付截图的临期促销文字、小数点误识别都会出错。这也是所有成熟记账 App 的做法。

#### 5.4.4 交互流程

```
[记一笔] 底部 —— 或 FAB 九宫格 —— 新增「拍照记账」
   ↓
选来源：拍照 / 相册
   ↓
OCR（移动端）→ 抽出字段 → 打开预填好的记一笔对话框
   ↓
用户确认/修正 → 保存（只写流水；原图用完即弃，不落库）
```

**原始截图不做保留**（用户决定）。图片只是 OCR 的输入，识别完就不再需要；留下来只会在附件目录里堆一批没人回看的文件。识别失败时退化成「手动记账」即可——用户自己知道金额，不需要一张图兜底。

#### 5.4.5 分享入口（强烈建议一起做，G16）

Android 的 `ACTION_SEND`（image/*）→ 从微信/支付宝截图后直接「分享到米记」→ 直接进 OCR 流程。

这一步把链从「截图 → 打开 App → 记一笔 → 拍照 → 选相册 → 找到图」压缩成「截图 → 分享 → 确认」，是体验质变。成本中等（`receive_sharing_intent` 之类的包，或自己写 platform channel）。iOS 有对应的 Share Extension，但需要 Xcode 工程改造，可延后。

**两个已踩过的坑，改动混淆配置时务必记得**：

1. **R8 缺类中断构建**。插件的 `TextRecognizer.initialize()` 是 `when(script)` 链，**编译期硬引用了全部语种**的 Options（天城文/日文/韩文），而 app 只引入拉丁 + 中文，插件又没带 `consumer-rules.pro`。release 开了 `isMinifyEnabled` 后，AGP 8 把 missing class 当致命错误。修法是 `proguard-rules.pro` 里 `-dontwarn com.google.mlkit.vision.text.**`。
2. **R8 删掉了 ML Kit 的注册器构造器**（更隐蔽）。ML Kit 靠「合并后 manifest 里登记的类名 + 反射无参构造」实例化 `ComponentRegistrar`，而 ML Kit AAR 自带的规则只写 `-keep class * implements com.google.firebase.components.ComponentRegistrar`——**保类不保成员**。R8 静态分析看不见反射路径，把三个 registrar 的 `<init>()` 删了，运行时初始化失败。修法是补上成员规格：

```proguard
-keep class * implements com.google.firebase.components.ComponentRegistrar { <init>(); }
```

**这类 bug 的识别特征：debug 包一切正常，只有 release 失效。** 排查不用连真机——`build/app/outputs/mapping/release/usage.txt` 是 R8 删了什么，`seeds.txt` 是保留了什么。

#### 5.4.8 识别率的瓶颈与提升手段

「识别不准」其实是两件完全不同的事，混在一起讨论会白费力气，先分清：

| 病症 | 表现 | 归属 |
|---|---|---|
| **认不出字** | 原文面板里文字残缺、乱码、整行缺失 | OCR 引擎 / 图像 |
| **认出来了没抽对** | 原文正常，但金额/商户空着或串到别的字段 | 解析（版面还原） |

**已排除：图像预处理。** 曾以为「放大 + 灰度 + 二值化」能提升小字识别率，实测**恰恰相反**：

| | 原图 | 2x 放大 + 灰度 + 自动对比度 |
|---|---|---|
| 支付宝截图金额 | `-18.40` | **`18.40`**（负号被吃掉） |
| 微信截图卡号 | `招商银行信用卡(9892)` | `招商银行信用卡(9892）>` |

负号被吃掉会把「支出」直接判成「收入」，是**有害的**。1170×2532 的手机截图分辨率本来就够，**保持原图直传**，不要画蛇添足。

**已做：用坐标还原版面（关键）。** 识别引擎给出的块顺序**不保证是阅读顺序**，而支付截图普遍是「左标签 + 右值」两列布局。丢掉坐标，`付款方式` 和 `招商银行信用卡(9892)` 就会错位，下游「找标签取值」必然取到隔壁字段——这是长篇排查后定位到的**主因**。

实现：`OcrLine` / `OcrPage.mergeVisualLines()`（`lib/core/ocr/ocr_line.dart`），按 **y 区间重叠**把同一水平行上的块并成一句。用重叠而不是「中心点接近」，是为了不误并上下相邻的两行。合并后再交给原有抽取逻辑，**解析规则一行没改**。

真实截图上的效果（左：合并前错位 → 右：合并后归位）：

```
付款方留言                  付款方留言  葛奕姝2027学琴费用，明年11月开始
葛奕姝2027学琴费用…         付款方式  招商银行信用卡(9892)
付款方式                    商品说明  叮咚买菜-2610102931172842272
招商银行信用卡(9892)         收款方全称  上海壹佰米网络科技有限公司
```

**已修：货币符号被误认会让金额整行失手。** 真机反馈「银行那张有 `- ¥ 18.4` 却说没识别到金额」，而微信（`-5000.00`）、支付宝（`-18.40`）都正常——三张截图的唯一差别就是**那张的金额带货币符号**：

| 截图 | 金额行 | 命中的是第几轮 |
|---|---|---|
| 微信 | `-5000.00` | ③ 整行只有金额 |
| 支付宝 | `-18.40` | ③ 整行只有金额 |
| 银行 | `- ¥ 18.40` | ① 带符号行——**符号一旦被认成别的字形，① 和 ③ 同时落空** |

`- ¥ 18.40` 里那个 `¥` 是紧挨着大字号数字的独立小字形，OCR 认成 `Y`、`￥`、甚至某个怪字形都有可能（本地用 RapidOCR 复现时它给的是 `￥`，所以这条只在真机上炸）。原来的第 ③ 轮要求「整行是纯数字」，一旦行里混进杂字就整行作废，于是金额为空。

修法：第 ③ 轮的判据从「整行是纯数字」改成「**剥掉前后不超过 4 个非数字字符后，剩下的是带小数点的金额**」（`^([^0-9]{0,4}?)(\d[\d,]*\.\d{1,2})([^0-9]{0,4})$`）。这样符号被认成 `¥`／`￥`／`Y`／任意单字都能捞回来，符号连同整行被吃掉只剩 `- 18.40` 也照样能捞。放宽的代价用两条限制兜住：**必须带小数点**（裸整数一律不认）、**装饰里不许有数字**（`1000 18.40` 不认）。

收支方向也跟着改成从「整段前缀」里找符号：前缀是一整坨（`- ¥ ` / `-Y ` / 空），只比对单个字符会漏掉。

**仍可继续提升的方向**（按性价比排序）：

1. **商户 → 分类规则库**（G3，批次 1）：截图本身不含消费分类，只有部分版式带「账单分类」。主要得靠商户关键词推断，兜底「未分类」。
2. **支付方式 → 本地账户匹配**：`付款方式 招商银行信用卡(9892)` 若能匹配到本地账户，可直接选中账户，而不只是填一个 `creditCard` 枚举。
3. **金额按字号加权**：支付页的金额字号最大，多个候选时应选最高的那个（`OcrLine.height`）。当前「带 ¥ 优先」已够用，列为备用手段。
4. **用户纠正后记住**：「这个商户我改过一次分类」→ 存成规则，下次自动命中。长期提升的主力。

> 底线不变：**OCR 结果一律回填表单让用户确认，绝不自动落账。**

### 5.5 方案 ③：支付通知捕获（G6）——已排除

> **用户已决定不做**（不申请 Android 通知读取权限）。本节保留为决策记录，说明它原本的定位与代价，便于日后重估。

这一条没在用户点名的例子里，但它原本的**性价比可能高于图片识别**。

**原理**：Android `NotificationListenerService` 监听支付宝、微信的通知，直接读出「微信支付 ￥38.50 已支付给 张三烧烤店」这类文本，正则抽金额/商户 → 生成一笔流水。

**为什么优于 OCR**：

|       | 通知捕获             | 截图 OCR      |
| ----- | ---------------- | ----------- |
| 用户操作  | **零**（付完就完事）     | 截图 + 分享/选图  |
| 覆盖率   | 所有支付宝/微信支付       | 只有用户记得截图的那些 |
| 金额准确度 | **精确**（通知文本里的金额） | OCR 可能错     |
| 时限性   | 实时               | 事后补         |

**与项目现有架构的契合度极高**：

- 项目有 `MoneyTransactionStatus.pending`（待处理，不占余额、不计统计）——**通知捕获一律先落 `pending`**。
- `MoneyReminderCenterItem` 已经有 `pending` / `completed` / `snoozed` / `ignored` 这套统一语义和「提醒中心」页面（`money_reminder_center_section.dart`）。**「待确认流水」天然可以挂在提醒中心里**，不需要新造 UI，只需要加一个来源类型。
- 用户确认时直接复用 `MoneyQuickActionLauncher` 的记账流程（预填好金额和商户）。

**成本与风险**：

- 需要写 Android 原生 `NotificationListenerService` + `MethodChannel`（项目目前没有自建 platform channel 的先例，属新增能力）。
- 用户必须去系统设置手动授予「通知使用权」——需要**清晰的中文引导页**（这是此类功能流失率最高的地方）。
- **合规风险**：通知读取属敏感权限，国内应用商店上架审核会重点问用途。需要隐私政策里明确写、且用途仅限记账。
- **iOS 完全不可能**（系统不开放）。

**结论**：值得做，但排在账单导入之后。建议作为「自动记账」的真正升级形态——现在模块里叫「自动记账」的东西其实只是「定时记账」（`money_auto_posting_entity.dart` 只有 daily/weekly/monthly 三种频率，没有条件触发），命名上有点名不副实。

### 5.6 方案 ④：分类规则引擎（G3）

**为什么是 P0**：导入 3000 条流水后，如果 2800 条是「未分类」，那这次导入的价值只剩「有记录」，统计页的分类占比、预算、异常分析全部失效。**分类规则是导入价值的放大器。**

**现状**：项目里叫「自动记账」的只有定时模板，**没有条件规则**。

**建议设计**：

- 条件（可组合，AND）：`商家包含 / 不包含`、`备注包含`、`名称包含`、`金额介于`、`账户等于`、`支付方式等于`、`来源等于（导入/OCR/手动）`、`时间段`
- 动作：设 `分类`、`子分类`、`标签`（追加）、`账户`、`支付方式`、`报销标记`
- 优先级：有序列表，先匹配先生效（沿用项目已有的 `sortOrder` 模式）
- 触发时机：**保存流水时**、**导入落库时**、以及**手动「对选中项套用规则」**

**存储位置（避免开新表）**：规则是纯配置、条目少（几十条量级）、不需要参与同步（各设备各配一套也无妨）。**建议序列化成 JSON 存 SharedPreferences**，参照 `money_dashboard_layout.dart:229-251` 的既有做法（它就是把这个思路用在看板布局上）。这样省掉 2.4 里那 6 步成本。

**UI**：设置 → 记账偏好 → 「自动分类规则」；或在流水页批量操作里加「套用规则」。

**首批内置规则**（开箱即用，覆盖高频导入场景）：商家含「美团/饿了么」→ 餐饮；含「滴滴/地铁/公交」→ 交通；含「超市/便利店」→ 日用；含「话费/流量」→ 通讯；等。种子数据可以参考 `money_seed_data.dart` 里已有的分类树。

### 5.7 其余（简要）

**账户余额对账（G8）**  
选账户 + 账期 → 算 `期初余额 + 收入 − 支出` 作为「应有余额」→ 用户输入 App/银行里的**实际余额** → 差异 → 引导补一笔「余额调整」流水。  
项目已有余额校正能力（`data/parts/accounts.dart`），可作为差异的落点，但需要给「余额调整」一个**专用来源标识**（正好用 G1 的 `source` 字段），这样统计页能把调整项剔除，不会污染消费数据。

**重复流水检测 / 合并（G9）**  
判定：同金额 + 时间差 ≤ 1 天 + 同账户 + 商家名相似（或一边为空）。命中后不自动删，而是出一个「可能重复」清单让用户勾选合并（合并 = 保留信息更全的一条 + 把另一条的标签合并过去 + 软删）。  
**注意**：导入去重（按 `externalId`，精确）和重复检测（按相似度，模糊）是两件不同的事，**前者必须做，后者是加分项**——所以 G9 优先级低于 G4。

**报销标记（G10）**  
加 `isReimbursable` + `reimbursedAt` 两个字段（可空/默认 false），加一个「待报销 / 已报销」筛选，加一张统计卡。现在只有一个内置的「报销」分类，无法回答「我还有多少钱没报下来」。成本很小。

**导出增强（G12）**  
现在是固定 14 列、上限 5000 条、CSV only（`money_export_service.dart`）。建议补：按**当前筛选条件**导出（现在导出的是全部）、xlsx 格式（需要 `excel` 包）、导出含附件清单。成本小。

**自动预算建议 / 储蓄目标（G13）**  
基于历史 3–6 个月均值推荐分类预算额度（预算模型已经很完整，只缺推荐逻辑）。储蓄目标可以是预算「收入目标」的镜像，或独立新表。

**「AI 报表」正名与增强（G14）**  
现状名不副实（纯本地聚合）。两个选择：① 改名「分析报表」，去掉误导；② 接 BYO-Key 的 LLM，把本地聚合结果喂给模型生成一段中文结论（「本月支出环比上升 18%，主要来自……，建议……」）。**② 的成本很低**，因为数据已经算好了，只是加一句文本生成。建议在 BYO-Key 决策通过后做。

| 2 | 桌面 / Web 编译验证 | 引入任何原生插件后跑一次 `flutter build windows / macos / web`，别把现有构建弄坏 |
| 3 | 报销标记与导出增强 | 排在批次 4 之后，按需再定 |

> **已无阻塞开工的决策。** 上表三项彼此独立，不要随时去掉都不影响其它部分。

## 八、明确不建议做的

| 项             | 原因                                                      |
| ------------- | ------------------------------------------------------- |
| 短信解析记账        | iOS 读不到第三方短信；Android 侧商店审核风险高、各家银行短信格式无限多，投入产出比最差       |
| 银行 API 直连     | 国内无面向个人的开放银行流水接口，只有企业级银企直连，不适用于本 App                    |
| 端侧跑多模态大模型     | 体积与性能代价（几百 MB + 发热）远超收益，且多端不可用                          |
| 在线多人协作        | 与「纯本地、无账号、无服务端」的核心定位直接冲突。真要做，等同于新增一个后端项目，应单独立项而不是塞进记账模块 |
| 一次性全量重写导入/OCR | 账单格式会变（支付宝自己就有两套 CSV）。必须走「表头驱动 + 可配置映射」，任何硬编码跳过行数的写法都会碎 |
