账户卡片重设计 + 账户流水弹窗

两件事：① 卡片按账户类型说该说的话 —— 现在信用卡、贷款、基金、预付卡共用同一套三行结构， 只靠「可用额度 / 当前余额」一个判断分支区分，贷款卡因此长得跟现金账户一样；② 点卡片不再跳走 —— 现在点整卡会切到「流水」面板并挂上账户筛选，用户回账户列表要手动切回来，而卡片上没有任何信号说明会发生这件事。 本稿给出新卡片、新弹窗，以及需要拍板的 6 个取舍。不改代码。

已实现（2026-10-20）
6 项取舍全部按推荐方案（A）落地：点卡片与「查看流水」打开同一个弹窗； 卡面显示「本月净」；按钮为底部动作行右侧的圆形图标（原稿是带文字的实心 pill， 上线后按要求只留图标——卡底已有一行对象级入口文字，再挤一个文字按钮会把长账户名 压成省略号；用途靠 tooltip + 语义标签说明）；初始余额移到弹窗概览； 贷款按负债渲染；弹窗底部保留「在流水中查看全部」。
代码：domain/account_card_info.dart（语义组与派生值）、 providers/account_flow_providers.dart（弹窗流水取数）、 presentation/accounts/account_detail_sheet.dart（弹窗）、 presentation/accounts/money_accounts_section.dart（卡面四槽位骨架）。
与稿子的另一处偏离：弹窗概览没有再做一份「筛选后合计」—— 同一屏出现两个总数会重犯「首页 hero 与记账格口径不一致」那类错， 概览只保留卡片同款的自然月合计。
修复：「近 90 天」原先把 DateTime.now() 直接减 90 天当查询区间， 而区间是 provider 的 family key —— 毫秒每帧都不同，key 每帧都变，列表永远转圈。 现在统一归一到当天零点。

现状 · 账户列表：银行、贷款、基金三种卡的结构完全一样， 只有信用卡多一条额度条与「账单 ›」。贷款卡显示负余额 + 初始负余额， 两个数字都不是用户想问的问题（「我还欠多少」「还了多少」）。
P1 · 类型差异只体现在「是不是信用类」
_AccountTileContent 只有一个分支：if (type.isCreditLike) 画额度条。 于是 贷款（loan） 落进了资产分支：主值打「当前余额 −¥486,200」、副值打「初始 −¥600,000」。 可它明明在「信用/负债」分组里（分组用的是 isCreditLike || isDebtLike，两处口径不一致）。
同类问题：投资账户只有「余额」，没有「本月涨跌」；预付卡只有「余额」， 而它真正的心智是「余额会花完」；储蓄与活期在卡上完全无法区分。
P2 · 点整张卡 = 离开这一页
onTap 直接调 _showAccountTransactions → _selectedPanel = transactions + 挂一条 accountId 筛选。 用户的真实意图九成是「看一眼这个账户最近花了什么」，代价却是：面板整屏被替换、 顶部多一个需要手动清掉的筛选、要看别的账户得先切回来。
而且卡面上没有任何「点了会跳走」的提示（没有 chevron）， 唯一的「查看流水」藏在 ⋯ 菜单里第 2 项。
P3 · 三个可点区域互相打架
信用卡卡面上同时存在：整卡点击（跳走）、「账单 ›」（开账单对账 sheet）、 ⋯ 菜单里「查看流水」、左滑「编辑 / 删除」。同一个矩形里有 4 种手势结果， 其中两种的目的地看起来一样。
P4 · 算了、传了，但没人用
currentUserAccountMonthlySummariesProvider 已经在 section 里取到，并且 逐卡传进了 _AccountTile(monthlySummary: …)——但 _AccountTile 从头到尾没有读过这个字段（只有 creditBill 被用了）。
更浪费的是聚合本身：SQL 的时间窗从上月初一直扫到本月末， 只为算出 previousIncomeMinor / previousExpenseMinor 两个全项目无人读取的字段。 也就是说每次打开账户页，都在为一个不显示的数字多扫一个月流水。 这一版要么把「本月净」用起来，要么连查询窗一起收窄。
P5 · 卡片高度不一致，列表参差
资产卡 3 行、信用卡 + 额度条、逾期时再加一行提示， 同屏卡片高低错落；分页每页 8 张，高度差直接影响「一屏能看几个账户」。

二信息模型：按「用户拿这张卡来回答什么问题」分类

不按 16 个枚举值逐个设计（那样会得到 16 套 UI），而是先归成 4 类语义组，再给每组一套固定骨架。 同一个组内只有「状态行」不同，卡片高度因此可控。
语义组 包含类型 主值 右侧辅助（1～2 个短值） 状态行 / 徽章
可花余额「我现在能花多少」 现金、银行、储蓄、支付宝、微信、云闪付、其他 当前余额 本月净变化 +¥2,000 / −¥1,240 无状态行（高度最矮）。非基准币加币种 chip；停用→整卡降透明度。
预付余额「还能刷几次」 预付卡 余额 本月已用 ¥44.00（只关心在减少） 余额 < 本月均耗 × 3 时给「余额偏低」提示；无字段则不做。
授信额度「我还能刷多少 / 这期还多少」 信用卡、花呗、白条、美团月付、其他信用 可用额度 本期应还 + 到期倒计时（已逾期 / 9 天后） 额度使用率条 + 「已用 / 额度」；≥80% 转琥珀、≥90% 转红。
负债「我还欠多少、还到哪了」 贷款（当前不可新建，只兼容历史/同步数据） 剩余欠款（正数） 已还比例（19%） 还款进度条 + 「已还 ¥113,800 / 本金 ¥600,000」+ 还款日。
持仓「值多少、涨了没」 投资 当前市值 本月净变化 +¥1,240 可选：占总资产 12%（需把净资产总额传进卡片，见第七节）。
为什么不是「每张卡都塞满」
现有卡片曾经是 8 层信息（名称、类型、账单日、3 个徽章、说明、本月对比长句、余额、额度明细）， 后来被压到 3 行，注释写得很清楚：「账户一多，一屏只能看 2 张」。 所以这一版的目标不是加信息，而是换掉错的信息：贷款卡去掉「初始 −¥600,000」， 换成「已还 ¥113,800 / 本金 ¥600,000」——同样的字数量，回答的却是用户真正的问题。
「初始余额」为什么移出卡面
它是建账时的输入值，不是当前状态。日常扫视时它只会和余额抢注意力； 而真正需要它的场景（对账、余额校正）本来就要打开弹窗。 移走后卡面空出来的位置给了「本月净变化」——这个数每个月都在变，才值得占视觉资源。

屏 1 · 资产组 + 授信 + 负债 + 持仓：四张卡高度约 100 / 140 / 140 / 100（dp），差异只来自「有没有额度条 / 进度条」。深色那张演示自定义 背景下的文字前景色规则（全部走 AccountCardScope，不写死白色）， 同时演示深色卡上的告警色要单独取亮档——主题琥珀在深底上对比不足。 底部左侧的空槽位是留给「对象级入口」的，没有就不填，不用来塞别的信息。
槽位 ①：名称行只放「会变的东西」
名称后的 chip 从「类型标签」换成状态：工资卡是用户自定义的 description 上限截断，其余可能值是 已停用 共享虚拟USD（非基准币才出现）。 类型本身已经在第二行 银行账户 · CNY 里了，不必重复。
槽位 ②③：主值只有一个，辅助值最多两个
主值的口径按组固定（余额 / 可用额度 / 欠款 / 市值），同组内永远同一口径， 用户扫视时不用每次都重新解读「这个大字是什么」。
辅助值只放「和主值直接相关、且每月会变」的数：资产放本月净、信用放本期应还 + 倒计时、 负债放已还比例、持仓放本月净。其余一切（初始余额、账单日、预算周期、开通时间）进弹窗。
槽位 ④：底部动作行
左边是对象级入口（目前只有信用卡有「账单详情 ›」，直接接现有的对账 sheet； 贷款暂时没有可去的对象级页面，就留空，不虚构入口），右边是「查看流水」。 这一行统一加一条虚线分隔，让「按钮」和「信息」在视觉上分开——现在「账单 ›」是夹在 金额右下方的一行小字，又像标签又像链接。
「查看流水」为什么做成实心按钮而不是文字链
它是这次唯一新增的可交互元素，必须一眼可发现：文字链在深色背景上会被金额压掉， 而且和「账单 ›」的视觉权重分不开。
落地后按反馈改成只留图标：卡底已经有一行对象级入口文字，再并一个「查看流水」 文字按钮，账户名一长就要省略号；用途交给 tooltip 与语义标签，读屏仍念得出「查看流水」。
同时把 ⋯ 菜单里的「查看流水」删掉，避免同一动作两个入口。
仍然保留的差异
停用账户：整卡 62% 不透明度 + 已停用，主值转次级色，仍可点开看历史流水（只读）。 虚拟账户：不加「余额校正」入口（现状已如此），卡面加 虚拟。

三·B状态变体：逾期 / 停用 / 遮罩 / 共享

这些状态现在都已经存在于数据里（isActive、isShared、isVirtual、 账单状态机、三态遮罩），但卡面上大多没有表达。新骨架把它们统一收进「名称行 chip + 辅助值颜色」两个位置， 不再为每种状态单独改布局。

屏 2 · 状态变体：逾期只改「辅助值颜色 + 一个红 chip + 进度条转红」， 结构不动；停用整卡降透明度并明说「只读 · 可查历史」；遮罩连「本月净」和底部收支一起打码， 避免从边角信息反推金额。
为什么不用整卡改色表示状态
卡面颜色已经被「自定义背景」占了（纯色 / 图片）。再让状态去改底色， 用户自定义的卡面就会被系统悄悄覆盖。状态只走文字与 chip， 唯一例外是额度条的填充色——它本来就是数据可视化，不是装饰。
遮罩要连「可推断的量」一起挡
这张卡原来是「余额打码、本月收支照常显示」。问题是收支一露，用户就能反推余额量级。 新规则：卡上任何金额字段都走同一个 hidden 状态，包括底部那行「收 · 支」。
共享 / 虚拟 / 非基准币：只加 chip，不加区块
这三个状态都只影响「怎么理解这个数」，不影响数字本身，所以给 chip 就够； 用 chip 也不用给每种组合单独排版（一张卡最多 3 个 chip，超了折行会被名称省略号吃掉，见实现注意）。

四点卡片 = 打开账户弹窗，不再离开这一页

一个弹窗承担「看一眼这个账户」的全部需求：概览口径与卡片完全一致（同一份数据、同一套月度合计算法； 金额在弹窗内不遮罩），下面是可筛选的流水，再往下是「在流水中查看全部」这个次要出口（老用户想批量编辑时仍能回去）。

弹窗 B · 信用账户：小额账单信息（本期应还、账单区间、最低还款、 额度使用率）压成一块，把卡面上原来分散的「本期应还 / 账单 › / 额度条」收进来； 对账与还款留在卡面的「账单详情 ›」（接现有的 CreditCardStatementReconciliationSheet）， 弹窗底部只保留两个通用入口：图标化的「在流水中查看全部」和「记一笔」。
弹窗尺寸与形态
复用 showAppResponsiveDialog(expandCompactSheet: true)：手机上是 圆角顶 + 可拖动、最大 88% 高的 bottom sheet，桌面上是 520dp 对话框。 与现有账单对账 sheet、余额校正 sheet 完全一致，不引入新的弹层语法。
「查看流水」按钮 vs 「点卡片」不是两条路
两者打开同一个 sheet、同一份数据。区别只在初始焦点： 点按钮 → 列表已展开并滚到第一条流水；点卡片 → 落在顶部概览。 这样就没有「两个相似弹窗各自维护」的成本，也不会出现「按钮里看到的数和卡片里不一样」。
为什么底部还留「在流水中查看全部」
弹窗只能看、不能批量改（多选批量改分类/账户是流水面板的能力）。 老入口的价值在于「批处理」和「跨账户搜索」，所以保留为次要图标按钮（名称走 tooltip）， 而不是继续让它占据整卡点击这个最高权重的入口。
底部两个动作都只留图标（已按此实现）
「在流水中查看全部」和「记一笔」原来都是文字按钮：320dp 上要换行， 而且它们只是对象级入口、不是这一屏的主任务。现在统一为图标 —— 左边 list_alt（次要，plain），右边 add（唯一写操作，填充态）， 名称由 tooltip + 语义标签承担，与卡底「查看流水」同一口径。
遮罩只留在卡面，不进弹窗（已按此实现）
账户页的隐藏是三态（显式显示 > 显式隐藏 > 全局遮罩），但只在卡片上生效。 第一版设计把遮罩也带进了弹窗，实测是反的：弹窗里没有眼睛开关， 用户点开看到 •••• 之后没有第二个入口能打开它，只能当成坏了。 现在弹窗（以及从弹窗点开的流水详情）一律展示真实金额 —— 「卡面遮住、点开才看得见」本身就是这个交互存在的意义。

六数据来源与实现要点

下面每个数都已经存在，不需要新表、不需要新聚合；唯一要新增的是弹窗的列表分页状态。
界面元素数据来源口径 / 坑
主值：余额 / 可用额度 / 欠款 / 市值 MoneyAccountEntity.displayBalanceMinor（信用是可用额度）、balanceMinor（贷款取 abs()） 贷款必须取绝对值 + 换标签，否则出现「−¥486,200」这种负余额。分组的判据要跟着一起改：isCreditLike || isDebtLike。
本月净 / 本月支出 currentUserAccountMonthlySummariesProvider（已存在，卡片目前没用） 只算 completed、排除转账与 transfer_in、退款按净额。转账不在里面，卡面写「本月净」时不要再写「收支」以免被理解成全量。顺带：这一版终于消费了它；若后续仍不用「上月」两字段，应把 SQL 的 previousStart 一起收窄。
本期应还 / 到期倒计时 currentUserCreditCardBillViewProvider(accountId) → toStatement() 状态机五档（未出账 / 待还款 / 临近 / 逾期 / 已还清），颜色取 error / warning，已经有一套。
额度使用率 usedCreditMinor / effectiveCreditLimitMinor 额度为 0 时不画条（避免除零），显示「未设额度」。
贷款「已还 / 本金」 initialBalanceMinor.abs() 当期初本金，1 - |balance| / |initial| 为已还比例 没有真实「本金」字段，这是用建账初始值反推的近似。文案要写「本金」而不是「总额」，并在弹窗里注明是「建账时录入」。
流水列表（弹窗） repository.listTransactions(userId, MoneyTransactionQuery(accountId: …)) 按 accountId 过滤时会包含转账两条（转出 / 转入各一条，转入带 transfer_in 标记）。所以列表能看到的比概览多，概览必须标「不含转账」。
弹窗小计（收入/支出/笔数） summarizeTransactions(userId, 同一 query) 与列表必须共用同一个 query 对象，否则「合计 5 笔、列表 7 条」。
待确认流水 status == pending 待确认不占余额、不进汇总。列表里正常显示 + 灰金额 + 待确认 徽章，概览另起一行「另有 2 笔待确认 ¥34.00」。
遮罩三态 _isEffectivelyHidden(accountId) + moneyAmountsMaskedProvider 只作用于卡面：弹窗与从弹窗点开的流水详情一律展示真实金额，不再透传遮罩状态（弹窗内没有开关，遮住就等于看不到）。
时间范围 / 类型筛选 dateStart / dateEnd / type（MoneyTransactionQuery 已有字段） 「近 90 天」用 DateTime.now() - 90d；「本期」直接用账单的 periodStart / periodEndInclusive，与账单对账口径一致。
多币种 账户自身 currencyCode 不做汇率换算（项目里也没有），弹窗所有金额用账户币种；非账本基准币时卡面与弹窗都要露币种代码。
性能 — 卡片不能为「查看流水」预先查数据：按钮只是打开弹窗，列表在弹窗首次 build 时才拉第一页（pageSize 10）。

一个必须先说清的取舍
弹窗里的流水行不复用 TransactionCard（它需要 accounts / 分类目录 / 分期 / 成员 / 账本 六个依赖，还有左滑、长按多选、批量条三套交互）。弹窗用的是只读紧凑行： 图标 + 标题 + 「分类 · 时间」+ 金额 + 状态徽章，点行打开现有的 TransactionDetailDialog。要编辑就进详情，不在这里做行内动作。

七需要你拍板的 6 个取舍

1 · 点卡片本体做什么？
  • A打开同一个账户弹窗推荐
    符合「卡片可点」的肌肉记忆，且不产生第二个弹窗。
  • B什么都不做
    只有「查看流水」和 ⋯ 菜单可点。最保守，但会让人反复戳卡片却没反应。
  • C仍然跳到流水面板
    与本稿目标冲突，不建议。
2 · 卡面显示「本月净变化」吗？
数据现成（monthlySummaries 已在 section 里取到了，只是没传给卡片）。 代价是每张资产卡都多一个会变的小数字；好处是「这张卡这个月在缩水」一眼可见。 推荐：显示，但只在非零时显示——零就换成「本月无收支」或不显示。
3 · 「查看流水」的形态
  • A底部动作行右侧的实心 pill推荐
    一眼可发现，与「信息区」用虚线分开。
  • B主值右侧一个「≡」图标按钮
    更省横向空间，但识别度差。
  • C整卡右下角箭头 chevron
    最轻，但与「点卡片跳走」的旧心智容易混。
4 · 「初始余额」从卡面移走，接受吗？
移到弹窗概览的最下面一行。卡面空出的位置给「本月净」。 如果你希望卡面仍然能对账，可以保留进 ⋯ 菜单，但不建议占主视觉—— 它是建账时的输入值，不是当前状态。
5 · 贷款账户要不要按「负债」单独处理？
  • A按负债卡渲染（剩余欠款 + 已还比例）推荐
    它已经不能新建（visibleMoneyAccountTypes 里没有 loan），只可能是历史或同步进来的数据； 成本很低，且能同时修掉「负余额」这个明显错误。
  • B暂不处理
    只保证不崩——但那样它还是会显示「−¥486,200」。
6 · 弹窗底部保留「在流水中查看全部」吗？
  • A保留为次要文字按钮推荐
    批处理、跨账户搜索仍需老面板，成本只是底部一行。
  • B去掉
    弹窗成为唯一入口，路径更短，但批量编辑能力就没有入口了。
